Agentic AI School 2026, Stage 2. Living document, filled in step by step.

## 1. Question (FINAL)

At each full hour **t** (Kyiv time), using only information available at t, predict the probability that **a new air raid alert begins in Kyiv city within (t, t + 60 min]**.

The forecast is made, trained, and evaluated **only at times when no Kyiv alert is active at t**.

**Target region:** м. Київ (city). Kyiv oblast is a separate region and is used only as an input feature.
**Forecast grid:** every full hour, Kyiv local time (handle DST correctly).
**Label:** 1 if a Kyiv city alert has start in (t, t + 60 min], else 0.
**Output:** probability in [0, 1].
### Definitions

**Active at t:** an alert with start <= t and (end > t or end unknown). An alert ending exactly at t counts as not active.
**Ongoing alert:** its end time is treated as unknown at t. Only elapsed = t - start may be used, never the total duration.

You’re not drifting; there’s just a lot of jargon stacked on one simple idea. Here’s the whole thing in plain terms.

What the “moving rate” actually is
The question is: “Kyiv isn’t under alert right now. What’s the chance a new one starts in the next hour?”

The simplest possible answer is a single number: out of all past hours with no alert, in what fraction did an alert start in the following hour?

All-history rate uses every hour since the dataset began. That’s one fixed number, roughly 6-10%.
Moving rate uses only the last 28 days before each forecast time. So the number changes over time. If the last month was intense, it says 22%. If the last month was calm, it says 7%.
That’s all it is: “the next hour will look like the recent past.” No features, no hour of day, no learning. It’s a rolling average. The “shrunk” part just means it’s blended slightly with the long-run rate when the recent window has few rows, so it doesn’t swing wildly.

Crucially, at forecast time t it only looks at outcomes up to t-1h, so there’s no leakage.

The decision path, as a story
You defined the question as onset in the next hour for Kyiv city, only when no alert is active. This is the harder, more honest version, because the trivial “already alerting, so yes” answer is excluded.
First experiments showed model type barely matters. Logistic regression and LightGBM landed within 0.003 log loss of each other.
The real discovery was drift. The positive rate per 14-day block ranged from about 7% (old) to 22% (newest). Swapping the all-history rate for the last-28-day rate cut log loss more than any model change did.
So the design became: logit(p) = logit(moving_rate) + small correction. LightGBM only learns the deviation from the moving rate.
Result: the moving rate is the solid win. The correction is basically noise on the test window.
Checking your two hypotheses
1) “The last two weeks are very different.” Yes, correct. The test positive rate is 22.1%, versus much lower historically. The all-history rate (about 10%) is therefore badly miscalibrated for this window, which is why it’s 0.12 worse. The moving rate adapts, and that’s its whole advantage.

2) “14 days makes the metric noisy.” Also correct, and you can see it in the output:

Only 299 test rows, with about 66 positives. That’s very little.
The bootstrap confidence intervals for LGBM and hour-factor include zero, so you can’t claim they’re worse or better than the moving rate.
ROC-AUC below 0.5 on the test (0.45) is meaningless at this size; it’s just random fluctuation around “no ranking signal”.
Calibration bins have 75 rows each, so a bin showing 0.30 predicted vs 0.16 observed is about 12 events of difference. That’s noise-level.
The rolling check over 6 blocks is your answer to the noise: LGBM wins 4 of 6 folds with a mean log loss of 0.440 vs 0.444. That’s a tiny edge, but it’s the more trustworthy number.

So “LightGBM failed” is too strong. More accurately: on the last 14 days it’s statistically indistinguishable from the baseline, and across 6 blocks it’s marginally better. The honest conclusion is “the moving rate carries almost everything, and the features add a very weak ranking signal.”

Quick, prototype-able improvements (45 minutes)
Ordered by value vs effort:

Tune the window and shrinkage of the moving rate. Try RATE_WINDOW_DAYS of 7, 14, 28, 56 and SHRINK_K of 5, 20, 50. Pick by the rolling 6-block mean, never by the test fold alone. This is two constants plus a loop, and it’s the highest-leverage change since the rate is where all the performance comes from.
Blend two rates. Average a 7-day and a 56-day rate (or feed both as features). A short window reacts fast, a long one is stable. Cheap to try.
Exponentially weighted rate instead of a hard 28-day cutoff, so yesterday counts more than 3 weeks ago. Same idea, a smoother weighting.
Add “regime” features like Kyiv alert counts over the last 7 and 14 days, so the model sees the current intensity directly.
Evaluate with more data per fold. Use 28-day test blocks in the rolling check to cut noise (more rows per fold), while keeping the 14-day test as the official one the task asks for.
Recalibrate lightly. If the correction model is overconfident (predicts 0.30, observes 0.16), shrink its output toward the moving rate: logit(p) = logit(rate) + 0.5 * correction. That one multiplier might be worth testing on the rolling folds.
